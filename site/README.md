# Documentation site

The public docs for `denex-network-manager`, built with [Astro](https://astro.build) and
[Starlight](https://starlight.astro.build) and published to
https://denex-io.github.io/denex-network-manager/.

This directory has its own Node/npm toolchain and is excluded from `deno fmt` and `deno lint`.

## Local development

Requires Node 22+.

```sh
deno task docs:install   # npm ci
deno task docs:dev       # http://localhost:4321/denex-network-manager/
deno task docs:build     # production build
```

Or directly, from this directory: `npm ci`, `npm run dev`, `npm run build`.

## Adding a page

1. Create a Markdown file under `src/content/docs/`, with `title` and `description` frontmatter.
2. Add it to the `sidebar` array in `astro.config.mjs`. The sidebar is explicit, not autogenerated, so
   ordering stays under your control.
3. Run `deno task docs:build` before committing.

Do not add an H1 or a hand-written table of contents — Starlight generates both.

Internal links need the base path, because this is a GitHub Pages project site:

```md
[CLI reference](/denex-network-manager/reference/cli/)
```

## The build is a real gate

`starlight-links-validator` fails the build on any broken internal link or missing heading anchor, and
`.github/workflows/docs.yml` runs it on pull requests as well as on deploys. A stale cross-reference
blocks merge rather than shipping quietly.

One consequence worth knowing: a bare `http://localhost:5082` in Markdown is autolinked and read as a
broken internal link. Wrap runtime URLs in backticks.

## Diagrams

Mermaid works in ` ```mermaid ` fences via `astro-mermaid`, which is ordered **before** `starlight` in
`integrations` so Expressive Code does not claim the fences first. Rendering is client-side with
automatic light/dark theme switching.

## Dependency pinning

`astro` and `@astrojs/starlight` are pinned to exact versions. Starlight ships breaking config changes
in minor releases, so read its changelog and re-run the build when bumping.

## Deployment

`.github/workflows/docs.yml` builds on every push and PR touching `site/`, and deploys to GitHub Pages
from `main`. Pages must be configured with "GitHub Actions" as its source in the repository settings.

Further conventions for agents are in [`../agents/docs-site.md`](../agents/docs-site.md).
